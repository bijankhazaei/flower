# Zeenome Web Frontend Architecture

## Architecture 
- **Pattern**: Modular Monolith with feature-based organization and clean separation of concerns.
- **Framework**: Next.js 15.1.7 with App Router
- **Language**: TypeScript with React 19
- **Styling**: Tailwind CSS + SCSS
- **Backend**: This project (even though written in NextJS) is not used for backend; 
No backend operations are made in the app; 
Backend is inside another project that provides REST API endpoints to this project. 
The token that is acquired from backend for authentication is saved into localstorage and therefore only CSR api calls are authenticated.
The architecture of api calls is similar to a ReactJS project (not NextJS) with one exception:
There might be some SSR api calls that are ONLY calling public unauthenticated api endpoints.

## **Important Rules and Regulations**

### Component creation, import and usability
Components fall into five major categories and based on the category, the actual component file and where it is located in the project, the way it is imported and used and the way it is named or exported is different:

- **Category 1: SSR components**:  (`src/app/**/**/page.tsx`, `src/app/**/**/layout.tsx`, `src/app/**/**/loading.tsx`)<br/>
This components are always written as async function components, they are always exported as default, and they are NEVER directly imported anywhere. 
If they render something, they MUST only render a CSR component of page-specific category. 
They can have API calls, but they MUST use api service instance from this path: `import { Api } from "@/services/apiService";`. They should never use any hooks directly.
If any hooks or CSR services should be used within them, there should be one component of page-specific category and render that component only and within that component hook should be used.
Here is an example: 
```tsx
import { Api } from "@/services/apiService";
import { redirect } from "next/navigation";
// Note that JourneyDetails is a page-specific CSR componenet and it is located inside _components directory next to this file
import JourneyDetails from "./_components/JourneyDetails";

// Next js SSR options can be exported
export const revalidate = 60;
export const dynamicParams = true;

// componenet is async and exported as default
export default async function Page({
  params: getParams,
}: {
  params: Promise<{ id: number }>;
}) {
	// Dynamic route paramters or query parameter or any thing in the next js backend of the request:
	const { id } = await getParams;
	
	// SSR API calls, no useApi hook is used. It uses { Api } from "@/services/apiService"
	const res = await Api.journeyItem(id);
	
	// SSR actions like redirection
	if (!res.ok) {
		redirect("/error/404");
	}
	
	// Only one page-specific CSR componenet is rendred, no direct render.
	return <JourneyDetails journey={res.data} />;
}
```

- **Category 2: Page specific components**: (`src/app/**/_components/*.tsx`)<br/>
These components are only used inside one SSR component or within each other; Meaning that they can only be imported inside other files in the same _components directory or inside an SSR component that is located just next to the _components directory. 
They are always located inside a directory (can have child directories) named _components, and this directory is always located next to SSR component where it used like a page.tsx component 
They contain nothing that could be reused in other parts of application; Reusable component are NOT in this category.

- **Category 3: Reusable custom UI components**: (`src/components/ui/**/**.tsx`)<br/>
All component that are not part of kit and could be reused in different parts of application are defined here, and they can be directly imported anywhere in the project.
They are basically the components that typically are created in a ReactJS application

- **Category 4: Reusable Kit components**: (`src/components/kit/**/**.tsx`)<br/>
Core design system components like inputs, buttons, grid, card, modal, etc... are created here. 
They MUST never be imported directly anywhere in the application.
They all follow strict type definitions in `src/contracts/ui` directory.
Their named and their type definitions are fixed and should never change. 
Their implementation is mainly ShadCN and Radic UI
They all must be imported and used via `Resolver` module
Here is an import and usage example:
```tsx
"use client";
import React from "react";
// Instead of button or other kit components, only resolver module is imported
import {Resolver} from "@/modules/resolver/Resolver";

const PendingOJBiologicalAge: React.FC = () => {
	// All kit components are accessible under Resolver namespace, like the Button componenet used below:
    return (
        <div className="flex justify-between md:items-center gap-4 max-md:flex-col">
            <Resolver.Button
                variant="dominant"
                className="max-md:w-full"
            >
                آغاز پرسش‌نامه
            </Resolver.Button>
        </div>
    );
};

export default PendingOJBiologicalAge;
```
A list of all kit components can be found in `src/contracts/ui/index.ts`

- **Category 5: layout components**: (`src/components/layouts/**.tsx`)<br/>
They are similar to page-specific components, the only difference is that they are only used within a layout SSR component.


### Api endpoints and api calls
- All api calls in this application must use `apiService` instance.
There are two instances available, 
  + SSR instance, used only is SSR components:
import it like this: `import { Api } from "@/services/apiService";` 
  + CSR instance, used in CSR components:
import it like this: `import { useApi } from "@/services/apiService/useApi";` and then get instance like this: `const api = useApi();`
- Both SSR and CSR instances return the same `ApplicationApiService` instance with minor differences that will be discussed later.
- The `ApplicationApiService` is basically an `axios` instance with the same methods in it. But they are customized a little bit:
The axios has these methods: get, post, put, patch, head and delete. These are the methods that are available in the apiService instance and their usage in exactly the same as axios.
- The base methods (get, post, put, patch, head and delete) MUST ONLY be used within action files (`src/app/**/**/actions.tsx`). These action files are basically define API endpoints.
- Every API endpoint must be defined inside an action file and action files automatically add methods to directly call that api endpoint within apiService instance.
Action files all have the same structure. Here is an example of an action file:
```tsx
// All action files import this
import { ApiActions } from "@/contracts/app/apiActions";

// All action files only export this structure as default
export default (
	// The input is apiService without actions. It is basically an axios instance
	(api: ApiType.RawService) => (
		{
            // The properties of this returned object are methods that call get, post, put, patch, head or delete methods of apiService. These methods are custom, their name MUST be unique within the whole application and they can get any kind of arguments
			journeyList: (page = 1, count = 10) =>
                // The return type of all API endpoints are declared in the call. And their actual type definition is below in the same action file
                // Note that this declared return type is always automatically wrapped in ApiResult<T> type which is declared in src/contracts/app/apiResult.tsx
				api.get<JourneyItem[]>(`/journeys?page=${page}&count=${count}`),
			journeyItem: (journeyId: number) =>
				api.get<JourneyItem>(`/journeys/${journeyId}`),
		}
	)
) satisfies ApiActions;

// The actual type definition of abow API endpoints 
export enum JourneyTypes {
	Once = "once",
	Multiple = "multiple",
	MultipleAction = "multiple-a",
}

export type JourneyItem = {
	id: number;
	name: string;
	type: JourneyTypes;
	slug: JourneySlugs;
	price: number;
	interval: number;
	re_buy_interval: number;
	is_free: 0 | 1;
	dependency_id: number | null;
	summary: string;
	description: string;
	extra: any;
	images: {
		id: number;
		url: string;
		name: string;
		order: number | null;
	}[];
	created_at: moment.Moment;
	updated_at: moment.Moment;
	cart_limitations: {
		maxCount: number | null;
		description: string | null;
		dependency: any;
	};
};
```
Now that this `actions.tsx` file is created inside `src/app` directory, the defined methods are automatically availabe in apiService instance everywhere in the application. Here is a usage example:
```tsx
"use client";
import { useApi } from "@/services/apiService/useApi";
const SomeComponenet: React.FC<> = () => {
	const api = useApi();
	const fetchJourneys = async () => {
		// The method journeyList that defined in action file can be accessed directly via apiService instance
		const res = await api.journeyList();
    }
    // *** rest of componenet
}
```
+ Differences between SSR and CSR apiService instances:
  + The authentication bearer token is saved in localstorage and is not accessible in SSR api calls, therefore only public unauthenticated api endpoints can be called in SSR instance.
  + The Token is automatically and implicitly added to authenticated users in CSR api calls. No need to manually add it in request.
  + All dates returned by backend server (meaning every string that matches ISO date string, the way the backend server sends date or datetime) in CSR instance is automatically converted into `moment` instance but in SSR calls they remain as strings. This is due to the way that SSR components pass data to CSR components. The moment object can not be serialized to be passed to csr components. 
    

### User specifications

#### Schema ('dark' or 'light')
- Always should be accessed or altered using `useSchema` hook exported from `schemaService`
- Also, these two tailwind class prefixes can be used to apply schema-specific styles: `light:` and `dark:`, eg: `light:bg-gray-700 dark:bg-gray-600`

#### Internationalization (`src/locales/`)
- **Multi-language**: English (`en/`) and Persian (`fa/`)
- **i18next**: React-i18next integration
- Everything that displays a text everywhere in the application should use `useLanguage` hook exported from `languageService`
- useLanguage hook returns i18n's `t` method along with some methods that control current language or available languages
- Translation files are located in `src/locales`, and they are automatically gathered together. The name of the file is the first part to be passed to the `t` method; e.g: `enums.genders.0` will map into enums.json file and then go to `genders` key and then `0` key
- Current language determines LTR or RTL system. The information of it is saved into `languageData.json` file inside translation files.
- The design system automatically changes the layouts and everything based on LTR or RTL language being used. 
- Furthermore, the two tailwind class name prefixed can be used to apply direction specific styles: `ltr:` and `rtl:`
- Never in anywhere in application left and right should be directly used in styling, always start and end MUST be used, eg: instead of `border-left:2px` this should be written `border-inline-end:2px`, or `margin-start` instead of `margin-right`, or in tailwind `ms` or `me` instead of `mr` and `ml`


### Authentication Logic (`src/modules/auth`)
- This module does everything about authentication in CSR. It also holds user profile and token data
- Access user data like this: `const user = useUser()` 

### State Management (`src/store/`)
- **Global Stores**: App, Cart, Journeys, Notifications, Observer
- **Atomic State**: Jotai for fine-grained reactivity
- **Complex State**: Zustand for feature stores

### Configuration (`src/configs/`)
- **Centralized Config**: API, App, Storage configurations
- **Environment Management**: Unified config exports
- Used like this: `AppConfig.nameOfFile.path.to.config.key`

### Utilities (`src/utilities/`)
- **Helpers**: Common utility functions
- **Hooks**: Custom React hooks
- **Transformations**: Data processing utilities
- **Validation**: Zod schemas with i18n
